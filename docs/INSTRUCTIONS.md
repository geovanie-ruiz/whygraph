# Whygraph — Agent Instructions

This project tracks architectural decisions in `.whygraph/graph/`. A whygraph
server must be running for full functionality. These instructions apply whenever
you are writing, modifying, or deleting code.

## Before Starting Work

Verify the whygraph server is running. If it's not, ask the user to start it with
`whygraph serve`, or start it yourself with their permission.

## Before Modifying Code

Call `whygraph_context(file)` via MCP for every file you are about to modify. This
returns existing architectural decisions and constraints for that area of the
codebase. Respect these constraints — if a decision says "X was rejected because Y,"
don't reintroduce X unless the conditions behind Y have changed.

If `whygraph_context` returns no decisions for a file, that area has no recorded
rationale. Write decision files for every architectural choice you make in that area.

## Capturing Decisions

Write decision files to `.whygraph/graph/` for every architectural choice you make.
A decision is any point where you:

1. **Chose between viable approaches** — even if one was clearly better. The "clearly
   better" reasoning is what a future agent needs.
2. **Followed a convention or pattern** a future agent might not know to follow.
3. **Configured something with specific values** — each configuration choice excludes
   alternatives.
4. **Modeled data in a specific way** — type shapes, required vs optional fields.
   Data modeling choices have deep downstream consequences.
5. **Chose NOT to do something** — deliberate omissions are decisions.
6. **Invented something not in the requirements** — scaffolding, helpers, workarounds.
   If it's not in the spec, document why it exists.

Write each decision as soon as you make the choice, not at the end of a session.
The reasoning degrades quickly — capture it while it's fresh.

### Decision File Format

Write one file per decision to `.whygraph/graph/`:

```yaml
---
id: <auto-generated NanoID>
label: Decision
title: <concise title describing the choice>
status: active
date: <YYYY-MM-DD>
affects:
  - <node ID(s) this decision touches>
tags: [<from: arch, data, security, performance, integration, infra, ux>]
created_at: <ISO 8601>
updated_at: <ISO 8601>
---

## Context
<the problem or constraint that created this fork — what were you solving?>

## Decision
<what you chose and how you implemented it>

## Tradeoffs
<what was gained AND what was lost — be specific>

## Alternatives
<other approaches you considered and WHY each was rejected>
```

**To find valid node IDs for `affects`:** Call `whygraph_list_nodes()` via MCP,
optionally filtering by label, parent, or search term.

**Quality bar:**
- Context explains the pressure, not just restates the title
- Tradeoffs name what was LOST, not just what was gained
- Alternatives explain WHY each was rejected

## Mapping Code Changes

When you **create a new file or module**, write a structural node file:

```yaml
---
id: <auto-generated NanoID>
label: Component            # or Feature for major functional areas
name: <human-readable name>
parent: <parent node ID>
status: active
refs:
  - file: <path to source file>
created_at: <ISO 8601>
updated_at: <ISO 8601>
---

Optional description.
```

When you **delete a module or feature**, set `removed_at` on the node file.
The server handles cascade removal of children and orphaned decisions.

When you **rename or move code**, update the `refs` field in the affected
node file to reflect the new path.

## File Naming

Decision and node files use the naming convention:

```
<nanoid>--<slug>.md
```

For example: `a1b2--use-websockets-for-live-updates.md`

NanoIDs are unique — collisions between concurrent agents are not a concern.

## Commit Decisions

Commit all decision and node files before ending your session. These files are
git-tracked and must be committed to survive.
