## What You Are Building

Whygraph is a repo-native architectural decision graph for agentic codebases. It captures _why_ a codebase is shaped the way it is — the rationale behind structural decisions, alternatives rejected, trade-offs accepted — in a format that AI agents can query before acting.

It is three things delivered as one package:

1. An **event log** at `.whygraph/events.jsonl` — append-only source of truth
2. A **graphology graph** — the runtime projection built by replaying the event log
3. A **CLI** (`whygraph`) and **MCP server** (`whygraph-mcp`) — interfaces to the graph

The architecture is event sourcing with a graph projection. The event log records what happened. The graphology graph is what you query. They are complementary layers, not alternatives.

The project validates itself. By the time it is working, `.whygraph/events.jsonl` in this repo should contain real decisions made during this build. Running `whygraph viz` should render those decisions as a working visualization. If the tool works on itself, it works.

---

## Done Looks Like

- `whygraph init` creates `.whygraph/events.jsonl` and appends an App node event
- `whygraph add` appends a valid decision event and its AFFECTS edge event
- `whygraph graph` renders the current graph as an ASCII tree
- `whygraph decisions` lists decisions with optional filters
- `whygraph timeline` renders the ASCII tree at a point in time
- `whygraph supersede` marks a decision superseded and records the replacement
- `whygraph viz` generates `.whygraph/viz/index.html` and opens it in the browser
- The viz renders nodes and edges as an interactive force-directed D3 graph
- The viz timeline scrubber replays the graph's evolution by replaying events up to a cutoff
- Clicking any node opens a side panel with full detail
- `whygraph-mcp` starts an MCP stdio server with all six tools responding correctly
- The MCP server is configured in `.claude/mcp.json` and queryable from Claude Code
- `.whygraph/events.jsonl` in this repo contains at least five real decisions made during this build

## Architecture: Event Sourcing + Graph Projection

### The Event Log

`.whygraph/events.jsonl` is an append-only log of graph mutation events. Each line is a JSON event. Events are never modified or deleted — they are the permanent record of what happened and when.

There are four event types:

```typescript
// A node was added to the graph
interface NodeAddedEvent {
  type: "node_added";
  timestamp: string; // ISO 8601, e.g. "2025-03-20T14:32:00Z"
  id: string;
  label: NodeLabel;
  properties: NodeProperties | DecisionProperties;
}

// An edge was added between two nodes
interface EdgeAddedEvent {
  type: "edge_added";
  timestamp: string;
  id: string; // unique edge ID, e.g. "edge-001"
  label: EdgeLabel;
  from: string; // node ID
  to: string; // node ID
}

// A node's properties were partially updated
interface NodePatchedEvent {
  type: "node_patched";
  timestamp: string;
  id: string; // node ID to patch
  properties: Partial<DecisionProperties>;
}

// An edge was removed (rare — used when superseding creates a structural change)
interface EdgeRemovedEvent {
  type: "edge_removed";
  timestamp: string;
  id: string; // edge ID to remove
}

type WhyEvent =
  | NodeAddedEvent
  | EdgeAddedEvent
  | NodePatchedEvent
  | EdgeRemovedEvent;
```

### The Projection

`projection.ts` replays the event log and builds a `graphology.MultiDirectedGraph`. This is the only way to get a graph — there is no other in-memory representation.

```typescript
import { MultiDirectedGraph } from "graphology";

// Replay all events and return the current graph
buildGraph(events: WhyEvent[]): MultiDirectedGraph

// Replay events up to and including the cutoff timestamp
// This is how temporal snapshots work — replay a subset of the log
buildGraphAt(events: WhyEvent[], cutoff: string): MultiDirectedGraph
```

Every node in the graphology graph stores its label and all properties as node attributes. Every edge stores its WhyEvent label (`COMPOSES`, `AFFECTS`, `SUPERSEDES`) as an edge attribute.

Replay logic per event type:

- `node_added`: `graph.addNode(id, { label, ...properties })`
- `edge_added`: `graph.addEdgeWithKey(id, from, to, { label })`
- `node_patched`: `graph.mergeNodeAttributes(id, properties)`
- `edge_removed`: `graph.dropEdge(id)`

### Why This Architecture

The event log is the source of truth because events are immutable facts. The graphology projection is what you query because graph traversal is what you need. Temporal replay is the natural operation of replaying a subset of the log — there is no special snapshot logic, just `buildGraphAt(events, cutoff)`.

This also means the visualization's timeline scrubber has a clean implementation: for each position on the scrubber, call `buildGraphAt` with the corresponding timestamp and re-render. The graph at any point in history is simply the projection of events up to that point.

| Label       | Required Properties                                                                      |
| ----------- | ---------------------------------------------------------------------------------------- |
| `App`       | `name`                                                                                   |
| `Feature`   | `name`                                                                                   |
| `Component` | `name`                                                                                   |

| Label        | Valid From → To                                                 |
| ------------ | --------------------------------------------------------------- |

### ID Rules

- Node IDs: lowercase, alphanumeric, hyphens only — `feat-auth`, `comp-session`
- Decision IDs: area-prefixed convention — `AUTH-001`, `CORE-002`
- Edge IDs: `edge-` prefix + sequential or uuid — `edge-001`
- IDs are immutable once written as events

## Core Modules

### `events.ts` — filesystem only

This module is the only code that touches `.whygraph/events.jsonl`.

```typescript
// Walk up from process.cwd() until events.jsonl found, or return null
findEventsFile(): string | null

// Return the path where events.jsonl should be created
getEventsFilePath(): string

// Load and parse all events from disk
// Skip blank lines, throw on malformed JSON
loadEvents(): Promise<WhyEvent[]>

// Validate then append a single event
// Never write if validation fails
appendEvent(event: WhyEvent): Promise<void>

// Append multiple events atomically (used by init and supersede)
appendEvents(events: WhyEvent[]): Promise<void>

// Create .whygraph/ directory and empty events.jsonl
// Append the initial App node_added event
// Throw if events.jsonl already exists
initEventLog(appName: string): Promise<void>
```

### `projection.ts` — pure, no filesystem

```typescript
import { MultiDirectedGraph } from "graphology";

// Replay all events into a graphology graph
buildGraph(events: WhyEvent[]): MultiDirectedGraph

// Replay events up to and including cutoff (ISO timestamp)
buildGraphAt(events: WhyEvent[], cutoff: string): MultiDirectedGraph
```

### `query.ts` — pure, takes a graphology graph

All functions take a `MultiDirectedGraph` as their first argument. No filesystem calls.

```typescript
// Get a feature node's ID, its component IDs, and IDs of decisions that AFFECT it or its components
getFeature(graph: MultiDirectedGraph, featureId: string): FeatureResult | null

// Get decision node IDs matching filters — all optional, AND logic
getDecisions(graph: MultiDirectedGraph, filters: {
  featureId?: string;
  componentId?: string;
  status?: DecisionStatus;
  after?: string;   // decisions with date >= after
  before?: string;  // decisions with date <= before
}): string[]

// Get the full decision chain for a node
// Uses graphology AFFECTS and SUPERSEDES edge traversal
// Returns decision IDs ordered by date ascending with chain links
getHistory(graph: MultiDirectedGraph, nodeId: string): DecisionChain[]

// Get a subgraph rooted at nodeId
// Uses graphology BFS over COMPOSES edges to depth
// Includes all AFFECTS and SUPERSEDES edges for returned nodes
getSubgraph(graph: MultiDirectedGraph, nodeId: string, depth?: number): MultiDirectedGraph

// Get all feature IDs in the graph (for error messages and MCP orientation)
getFeatureIds(graph: MultiDirectedGraph): string[]

// Get full node attributes by ID
getNodeAttributes(graph: MultiDirectedGraph, nodeId: string): NodeAttributes | DecisionAttributes | null
```

Use graphology's built-in methods:

- `graph.neighbors()`, `graph.outNeighbors()`, `graph.inNeighbors()`
- `graph.edges()`, `graph.outEdges()`, `graph.inEdges()`
- `graph.getNodeAttribute()`, `graph.getEdgeAttribute()`
- BFS from `graphology-traversal`: `bfsFromNode(graph, nodeId, callback)`

### `validate.ts`

```typescript
validateEvent(event: WhyEvent): { valid: boolean; errors: string[] }
```

Validation rules:

- `id` matches `/^[a-z0-9-]+$/` for nodes; edge IDs match `/^edge-[a-z0-9-]+$/`
- `timestamp` is a valid ISO 8601 string
- `date` on Decision properties matches `YYYY-MM-DD`
- Decision `node_added` events include all required DecisionProperties fields, none empty
- `EdgeAddedEvent` label respects the allowed hierarchy:
  - `COMPOSES`: from label must be App/Feature/Component, to label must be Feature/Component — validate by looking up node labels in a partial graph built from prior events
  - `AFFECTS`: from must be Decision
  - `SUPERSEDES`: from and to must both be Decision
- `NodePatchedEvent` only patches known Decision properties

## CLI Reference

All commands find `.whygraph/events.jsonl` by walking up from `process.cwd()`. Missing file → clear error directing to `whygraph init`.

### `whygraph init [app-name]`

Prompt for name if not provided. Create `.whygraph/events.jsonl`. Append `node_added` event for App. Offer to add initial features interactively. Error if events.jsonl already exists.

### `whygraph feature add --id <id> --name <n> [--parent <id>] [--description <text>]`

### `whygraph component add --id <id> --name <n> --parent <id> [--description <text>]`

Append `node_added` + `edge_added` (COMPOSES) events.

### `whygraph add --id <id> --title <title> (--feature <id> | --component <id>) [options]`

Options: `--context`, `--decision`, `--tradeoffs`, `--alternatives`, `--date` (default today).
Prompt interactively for any missing required fields. Never write an incomplete decision.
Append `node_added` (Decision) + `edge_added` (AFFECTS) events.
Timestamp both events with the current ISO time.

### `whygraph supersede <old-id> --new-id <id> --title <title> [options]`

Append in order:

1. `node_added` event for the new Decision
2. `edge_added` event for SUPERSEDES (new → old)
3. `node_patched` event for the old Decision: `{ status: "superseded", supersedes: new-id }` — wait, the old decision is superseded _by_ the new one. Patch old with `{ status: "superseded" }`. The new decision's `supersedes` property is set in its own `node_added` event.

### `whygraph graph [--feature <id>] [--depth <n>]`

Load events → build graph → render ASCII tree.

```
Whygraph
├── Core Graph (feat-core)
│   └── [CORE-001] JSONL over SQLite (active) — 2025-03-20
└── CLI (feat-cli)
    └── [CLI-001] Commander over yargs (active) — 2025-03-20
```

### `whygraph decisions [--feature <id>] [--component <id>] [--status <s>] [--after <date>] [--before <date>]`

Load events → build graph → query → print table: ID, title, status, date, affects.

### `whygraph timeline [--at <timestamp>] [--before <decision-id>]`

Load events → `buildGraphAt(events, cutoff)` → render same ASCII tree.
If `--before <decision-id>`: find that decision's timestamp in the event log and use it as the cutoff.

### `whygraph viz [--out <path>] [--no-open]`

Load events → build current graph → serialize to JSON → generate HTML → write to `.whygraph/viz/index.html` (or `--out` path) → open in browser unless `--no-open`.

## MCP Server

Stdio server. Configured at `.claude/mcp.json`:

```json
{
  "mcpServers": {
    "whygraph": {
      "command": "npx",
      "args": ["whygraph-mcp"]
    }
  }
}
```

**Reload on every tool call.** Call `loadEvents()` then `buildGraph()` at the start of every tool handler. Never cache across calls — the CLI may have appended events between calls.

**Return full text.** Never truncate decision properties in responses.

**Return IDs, not objects, internally** — but serialize full node attributes in MCP responses so the agent gets everything it needs in one call.

### Tools

**`whygraph_get_feature(feature_id: string)`**
Load → build → `getFeature()`. Returns full node attributes for feature, all components, and all affecting decisions. On not-found: return error listing available feature IDs from `getFeatureIds()`.

**`whygraph_get_decisions(filters: { feature_id?, component_id?, status?, after?, before? })`**
Load → build → `getDecisions()`. Returns array of decision node attributes with full properties.

**`whygraph_get_history(node_id: string)`**
Load → build → `getHistory()`. Returns decision chain with full node attributes and chain links.

**`whygraph_get_subgraph(node_id: string, depth?: number)`**
Load → build → `getSubgraph()`. Returns serialized subgraph with full node and edge attributes.

**`whygraph_add_decision(id, title, affects[], context, decision, tradeoffs, alternatives, date?)`**
Load → build → validate `affects` IDs exist → append events. Return full created decision attributes on success, detailed error on failure.

**`whygraph_supersede(old_decision_id, new_id, title, context, decision, tradeoffs, alternatives, date?)`**
Load → build → validate old decision exists and is active → append events. Return both old and new decision attributes.

## Visualization

`whygraph viz` generates a single self-contained HTML file. D3.js v7 from CDN. No server, no build step. The file opens via `file://`, can be committed to the repo, and served on GitHub Pages.

### Data Embedding

The CLI serializes two things into the HTML as embedded script data:

```html
<script>
  const EVENTS = [ /* full WhyEvent array, sorted by timestamp */ ];
  const CURRENT_GRAPH = { nodes: [...], edges: [...] };
  // nodes: [{ id, label, ...attributes }]
  // edges: [{ id, label, from, to }]
</script>
```

`EVENTS` is used by the timeline scrubber to rebuild the graph at any point in time using a JavaScript port of the projection logic. `CURRENT_GRAPH` is used for the initial render.

### Projection in JavaScript

The HTML file includes a self-contained `buildGraphAt(events, cutoff)` function written in plain JavaScript (not TypeScript). This mirrors `projection.ts` exactly. The timeline scrubber calls this function with different cutoff values and passes the result to D3 for re-rendering. No network calls, no server, no module imports — just the embedded events array and a pure function.

### Layout

Force-directed graph using `d3.forceSimulation`:

```javascript
d3.forceSimulation(nodes)
  .force(
    "link",
    d3
      .forceLink(edges)
      .id((d) => d.id)
      .distance((d) => (d.label === "COMPOSES" ? 80 : 140)),
  )
  .force("charge", d3.forceManyBody().strength(-300))
  .force("center", d3.forceCenter(width / 2, height / 2))
  .force("collide", d3.forceCollide(30));
```

### Node Visual Treatment

| Label                   | Shape   | Radius | Fill                         |
| ----------------------- | ------- | ------ | ---------------------------- |
| `App`                   | Circle  | 24     | `#1e293b`                    |
| `Feature`               | Circle  | 18     | `#2563eb`                    |
| `Component`             | Circle  | 12     | `#93c5fd`                    |
| `Decision` (active)     | Diamond | 14     | `#f59e0b`                    |
| `Decision` (superseded) | Diamond | 14     | `#d1d5db` with dashed stroke |
| `Decision` (deprecated) | Diamond | 14     | `#ef4444` at 50% opacity     |

Diamond shape: render as a `<rect>` rotated 45 degrees via `transform="rotate(45)"`.

Node labels render below each node as `<text>` elements. Decision nodes show the ID; other nodes show the name.

### Edge Visual Treatment

| Label        | Stroke    | Style                                             |
| ------------ | --------- | ------------------------------------------------- |
| `COMPOSES`   | `#475569` | Solid, width 1.5                                  |
| `AFFECTS`    | `#f59e0b` | Dashed `[4,3]`, width 1                           |
| `SUPERSEDES` | `#94a3b8` | Dotted `[2,3]`, width 1, arrow to superseded node |

All edges render with arrowhead markers. Use D3's `<defs>` marker pattern.

### Timeline Scrubber

Position: fixed at bottom of viewport, full width, 60px height.

```html
<div id="timeline">
  <span id="timeline-label">2025-03-20</span>
  <input type="range" id="scrubber" min="0" max="100" value="100" />
</div>
```

The scrubber maps 0–100 to the range of timestamps in `EVENTS`. On input:

1. Compute the cutoff timestamp from the scrubber position
2. Call `buildGraphAt(EVENTS, cutoff)` — pure JavaScript, returns `{ nodes, edges }`
3. Update the D3 simulation with the new nodes and edges
4. Nodes outside the current window render at 10% opacity (they don't disappear — you can always see the full eventual structure)
5. Update the label to show the current date

### Side Panel

Right-aligned, 320px wide, full viewport height, slides in on node click via CSS transition.

**Feature or Component node:**

- Name (heading)
- Description if present
- Section: "Decisions" — list of decisions that AFFECT this node, ordered by date
- Each decision: ID badge + title + status chip + date
- Click any decision in the list to re-open the panel for that decision

**Decision node:**

- ID (monospace) + status chip
- Title (heading)
- Date
- Labeled sections in order: Context, Decision, Trade-offs, Alternatives
- "Affects" list: node IDs as chips, click to open that node's panel
- If `supersedes`: "Supersedes [ID]" link
- If `status === "superseded"`: "Superseded by [ID]" link

Close button top-right. Click on graph background also closes.

### Interactions

- Pan and zoom: `d3.zoom()` on the SVG container
- Drag nodes: `d3.drag()` per node, updates simulation position
- Click node: open side panel
- Click SVG background: close side panel
- Hover node: show tooltip (name or ID + title) via a floating `<div>`

## Design Constraints

**Events are immutable.** `events.jsonl` lines are never modified or deleted. They are facts. The only way to change the graph state is to append new events.

**Validate before append.** Every `appendEvent` call validates the event first. A malformed event must never reach the file.

**No external database.** The event log is JSONL. The runtime graph is a graphology instance. No SQLite, Neo4j, or other storage dependency.

**MCP reloads on every call.** Load events and rebuild the graph at the start of every tool handler. The CLI may have appended events between calls.

**Full text in MCP responses.** Never summarize or truncate decision properties.

**IDs are immutable.** Once an ID appears in a `node_added` or `edge_added` event, it cannot change.

## CLAUDE.md

```markdown
# Whygraph

## What This Is

A repo-native architectural decision graph for agentic codebases.
See README.md for the full description and docs/spec/WHYGRAPH_SPEC.md for the build spec.

## Architectural Memory

This project tracks its own decisions in .whygraph/events.jsonl.

Before modifying any feature area, read relevant decisions:

# Before the CLI exists — query directly

cat .whygraph/events.jsonl | grep '"affects".\*<feature-id>'

# Once the MCP server is running

whygraph_get_feature("<feature-id>")

## Writing Decisions

When you make a significant implementation decision, append it to the event log.
Use whygraph add once the CLI works. Before that, append events manually.
Do not ask for permission — write decisions as you make them.

A decision is significant if it represents a fork: a choice between two or more
approaches where the rationale for the chosen approach is not obvious from the code.

## Conventions

- ESM throughout — .js extensions on imports in TypeScript source
- Named exports only — no default exports
- Validate before every append — never skip validation
- Tests before shipping each core module — vitest, >90% coverage on src/core/
- graphology is the graph — do not build parallel data structures
```
